## 0. 一句话结论

战斗里装哪一套技能，由**备战界面选中的角色**决定；
`PLAYER_SKILLS` 从"通用一套"变成"两个角色技能表的**并集**"，
而"这一局装什么"由 `data/content.ts` 的 `skillsForPlayer(id)` +
`app/deps.ts` 的 `registryFor(playerId)` 装配。

**新增 3 个技能**（劈 / 拳 / 卸）、**新增 1 个引擎机制**（阈值抵消）、
**每人一套血上限**（150 / 120）、**「卸」取代了「防」**。

## 1. 两套技能（定稿）

### 1.1 林晚风（id `'player'`）—— 剑士，150 血，攻守均衡

| 技能 | id | 代价 | 读条 | CD | 效果 | 状态 |
|---|---|---|---|---|---|---|
| **斩** | `attack` | 炁 15 | 500ms | — | 伤害 10 | ✅ 不动 |
| **劈** | `pi` | 缠 **50** | **1200ms** | — | 伤害 **45** | 🆕 |
| **凝** | `focus` | 缠 50 | 0 | — | 增伤 +20%（30s） | ✅ 不动（与凯丽**共用**） |
| **卸** | `guard` | 免费·**按住 3 炁/秒** | 0 | — | **阈值抵消**（见 §3） | 🆕 |
| **避** | `dodge` | 炁 15 | 0 | 1s | 无敌 0.5s | ✅ 不动 |

⚠️ **林晚风没有「截」也没有「闪」** —— 这两个都归凯丽。
「卸」的 `tags` 里**没有** `dodge`：被 Boss「碾压」打倒在地时
（`BuffFlags.restrictToTags`），她的出路是**「避」**（它带 `dodge`）。

### 1.2 凯丽（id `'kaili'`）—— 斗士，120 血，快节奏

| 技能 | id | 代价 | 读条 | CD | 效果 | 状态 |
|---|---|---|---|---|---|---|
| **拳** | `punch` | 炁 **15** | **250ms** | — | 伤害 **6** | 🆕 |
| **轰** | `blast` | 缠 50 | 900ms | — | 伤害 30 + 易伤 | ✅ 不动 |
| **凝** | `focus` | 缠 50 | 0 | — | 增伤 +20%（30s） | ✅ 不动（共用） |
| **截** | `jie` | 炁 10 | 0 | 10s | 打断 + **成功退还 CD** | ✅ 保留（派生已去掉） |
| **闪** | `flash` | 免费 | 0 | 0.6s | 无敌 0.1s | ✅ 不动 |

⚠️ **凯丽没有「避」，也没有「防」/「卸」** —— 她的防御手段是「闪」。
这不是漏了：她的技能表里没有那两个 id，是**结构性**的。
⚠️ 「闪」带 `dodge` tag，所以它是她**倒地时唯一的出路**。

### 1.3 为什么这么分（判断）

| 判断 | 理由 |
|---|---|
| **两人共享「凝」** | 定稿里两人的「凝」是同一个技能（同代价/读条/效果）。所以它是 `kits/shared.ts` 里的**同一个定义对象**，两边都 import —— 不是"两份恰好一样的东西"（那样改一个就会漂） |
| **防御机制按节奏分** | 林晚风"适中/攻守均衡" → 「卸」要**预判 + 付炁**（按住 3/秒）；凯丽"快/注重反应" → 「闪」**不花炁但窗口只有 0.1 秒**，要按得准 |
| **重击按角色分叉** | 「轰」50 缠 / 0.9s / 30 伤 + 易伤；「劈」50 缠 / **1.2s** / **45 伤**。劈**没有**附带效果，所以它换来的是纯伤害 —— 而那必须用"全表最长的读条"付账 |
| **普攻按节奏分叉** | 「斩」15 炁 / 0.5s / 10 伤；「拳」15 炁 / **0.25s** / **6 伤**。两者都受**炁**限制（每秒回 10），所以"打得快"的真实代价是**更早空炁** —— 这正是凯丽"注重资源分配"的落点 |
| **「击」保留、但暂时无产出者** | 用户原话："放到 p3 或者初始化炁机的地方再实现"。见 §4 |
| **「破」留给黛玄** | 它在她（还没做）的技能表里。⚠️ 2026-10-12 第二次重标定后它**不属于任何角色、不在设置页**，见 §6 |

## 2. 技能从哪来（代码结构）

```
src/data/kits/
├── shared.ts        「凝」+ 它的 buff（两个角色共用，谁都不依赖谁）
├── linwanfeng.ts    斩 / 劈 / 卸 / 避 + 血上限 150
├── kaili.ts         拳 / 轰 / 截 / 闪 + 易伤 + 血上限 120
├── combo.ts         「击」+派生窗口「combo-window」（P3 由炁机接回）
└── reserved.ts      「破」+ `PENDING_SKILLS`（黛玄的待接线技能，见 §6）
```

`src/data/content.ts`（原 629 行 → 现在只做汇总）保留三件事：

1. **汇总**：`PLAYER_SKILLS` = 两个 kit **并集** + `STRIKE`；
   `ALL_SKILLS` = 它 + `PENDING_SKILLS`（「破」）+ 各 Boss 的技能
2. **归属判据**：`PLAYER_SKILL_IDS` / `BOSS_SKILL_IDS`（"这个 id 是谁的"的
   **唯一真相** —— 不许用 id 前缀猜，那是踩过的坑）
3. **装配入口**：`skillsForPlayer(id)` / `playerSkillIdsFor(id)` / `PLAYER_KITS`

⚠️ **`PLAYER_SKILLS` 是"内容全集"，不是"这一局带什么"**。两个消费者都是
全局的：内容注册表（引擎要按 id 解析）与设置页的按键列表（整场游戏可绑
哪些）。而"这一局装哪 5 个"是另一件事。

### 2.1 装配链路（唯一的）

```
备战界面选中 playerId
  → app/battleSetup.ts  registryFor(playerId)      ← 引擎只认识这 5 招 + Boss 招
                        bindingsForPlayer(...)     ← 键位表按技能集过滤
                        slotsFromBindings(...)     ← 技能栏由过滤后的键位表派生
  → core 引擎（skills = 注册表）
  → app/touchControls.ts  currentSkillIds()        ← 触屏双弧由**引擎的技能集**过滤
```

**三处派生面（技能栏 / 触屏双弧 / 设置页）都是机械派生的**，没有硬编码
技能个数或顺序：

| 位置 | 它读什么 | 换角色时 |
|---|---|---|
| 技能栏槽位 | `slotsFromBindings(filtered bindings)` | ✅ 自动 |
| 触屏双弧 | `touchButtonsFromBindings(filtered bindings)` | ✅ 自动 |
| 设置页按键行 | `registry.skills`（**并集**，刻意不按角色过滤） | 不变（见下） |

⚠️ **设置页故意不按角色过滤**：那张表是"整场游戏可绑哪些技能"，而玩家的
改键是**一份**（`settingsStore`）。按角色过滤会让"切换角色 → 键位列表
悄悄变了"，而玩家以为自己改的是全局的。代价是林晚风也能给「截」绑一个
她按不出来的键（她那一局里没有它）；这比"键位表随角色漂"小得多。

⚠️ **触屏过滤的判据是"引擎的技能集"**，不是另抄一份角色表 ——
引擎收到的表就是这一局的真相，两边**结构上不可能漂**。

### 2.2 出厂键位

一个键只出现**一次**（并集推导出的默认技能栏不能有两格同键）：

一个键只出现**一次**，而且**每个技能都有自己的键**：

| 键 | 技能 | 归属 |
|---|---|---|
| `Q` | 斩 | 林晚风（普攻） |
| `W` | 轰 | 凯丽（重击） |
| `E` | 凝 | **两人共用** |
| `R` | 截 | 凯丽（打断） |
| `A` | 闪 | 凯丽（无敌） |
| `S` | 避 | 林晚风（无敌） |
| `D` | 拳 | 凯丽（普攻） |
| `F` | 劈 | 林晚风（重击） |
| `G` | 卸 | 林晚风（按住卸力） |

⚠️ **「破」不在这张表里**（2026-10-12 第二次重标定）：它是黛玄的待接线
技能，不属于任何角色，所以不可绑键、也不进设置页。见 §6。

⚠️ 过滤之后的**默认技能栏恰好是 5 格**（`slotsFromBindings` 过掉空键）：
林晚风 = `Q(斩) F(劈) E(凝) S(避) G(卸)`；凯丽 = `W(轰) E(凝) R(截) A(闪) D(拳)`。
所以**每人开一局都看到 5 个按钮**。

⚠️ **"默认不绑键、但设置里能绑"这条机制本身还在**（它服务的是"真的属于
某个角色、只是默认没键"的技能，如凯丽的「截」）：`DEFAULT_BINDINGS` 是
"可绑技能的全集"，战斗画面只画**绑了键的**。`tests/unit/keyRows.test.ts`
有一条断言强制"每个可绑技能都在这张表里"（踩过的坑：「截」漏在表外 →
设置页显示得出来却绑不上，绑定静默丢失）。

⚠️ **并集里同时有「轰」/「劈」（都是重击）与「闪」/「避」（都是无敌）** ——
设置页会同时列出它们（那是全集，不随角色变）。这是刻意的：
玩家改的是**一份**键位表，而他会在两个角色之间来回切（§2.1）。

## 3. ⭐「卸」的规则（阈值抵消）

### 3.0 名字：为什么叫「卸」（以及为什么 id 还叫 `guard`）

用户定稿（2026-10-12 晚）：显示名从**「格」改成「卸」**（用户原话：
"卸 可以"）。他的判断过程：

| 候选 | 行不行 | 为什么 |
|---|---|---|
| **格** | ✗ | 更像**盾牌**的动作，而林晚风是**剑士** |
| **招 / 架** | ✗ | 都是**一次性动作**，而这个技能是**按住不放**的 |
| **卸** | ✓ | `≤N` → "**卸掉了**" ✓；`>N` → "**卸掉 N 点**" ✓；"**按住卸**" ✓ —— 两半规则与"持续动作"**同时成立** |

（反例正是判断依据："格掉 15 点" / "架掉 15 点" 都**说不通**。）

**动了什么**：i18n 的显示名 / 描述 / 提示文案（`skill.guard.name` /
`skill.guard.desc` / `hint.guard` / `hint.dodgeOrGuard` / 各 Boss 描述里的
"可格挡"）。

**没动什么、以及为什么**：技能 id 与常量名**仍是** `guard` /
`GUARD` / `GUARD_*` / `GUARD_THRESHOLD` / `GUARD_HOLD_DRAIN_PER_LOGIC_TICK`。

1. **`skillId` 是持久化键**：`app/settingsStore.ts` 把键位表按 skillId 写进
   localStorage。改 id 会让老玩家给这一招改过的键**静默丢失**（回落到默认 `G`）
2. **技能 id 同时是 `RunRecord.battleStats` 的键**（那一层有自己的版本号）
3. **本仓库已有先例**：`douqi` / `energy` 的中文名在 2026-10-09 对调过，
   标识符出于历史原因保留（`data/balance.ts` 文件头："改中文名只动
   `i18n/locales/`"）

所以规矩是：**显示名跟着玩法改，标识符跟着历史留 —— 但"名字不准确"
必须写下来**（本节 + `kits/linwanfeng.ts` 的 `GUARD` + `data/balance.ts`）。

⚠️ **以后可能做的事（现在明确不做）**：用户提过"名字可以按角色不同 ——
剑士用剑的动作、法师用盾"。那需要**每个角色一份技能显示名**（现在
`SkillDef.nameKey` 是全局 key，两人共用的「凝」也是同一个 key），
而黛玄还没做 —— 记在这里，**不要现在实现**。

⚠️ 这次改名**不改变任何确定性语义**：`GOLDEN_OUTCOME` 一分未动
（`tests/golden/replay.test.ts` 全绿且数值不变）。

### 3.1 规则（用户定稿，逐字）

```
这一击的伤害 ≤ N  →  完全抵消（0 伤害，且【连它带的效果一起免】，如眩晕）
这一击的伤害 >  N  →  伤害 − N（效果【照吃】）
```

- **判据是"这一击结算出来的伤害值"**：含增伤 / 易伤（`preBlockDamage`），
  **不含**防御侧减免 —— 阈值就是拿它来判的。
- **多段攻击按【每一段】各减一次**（用户已确认）。
  两段各 20 → `2 × (20 − N)`，不是 `(20+20) − N`。
- **`≤` 是闭区间**：伤害恰好等于 N 也完全抵消。

### 3.2 `N` 的口径

**`N = GUARD_THRESHOLD = 15`**，住在 **`src/data/balance.ts`**。

用户的调参口径是"**如果太强，阈值可以改成 10**" —— 所以它必须是一个
**具名常量**：内容（`kits/linwanfeng.ts` 的 `GUARD_THRESHOLD_BUFF`）import
它，**不在内容里散落魔法数**。改阈值只需改一处。

⚠️ 它与「按住消耗」是**一对**杠杆，两个一起记在 §3.5。

### 3.3 它复用了哪些已有能力（**两半都不是新造的**）

| 规则的一半 | 复用的通路 | 怎么复用 |
|---|---|---|
| **`≤N` 整击作废** | **`invulnerable` 的 `avoided` 通路** | `resolveHit` 里 `avoided` 现在有两个来源（无敌 / 阈值）。走同一条路 → **"连眩晕这类效果一起免"是天然的**（`applyHitEffects` 里那段"作用在挨打者身上的效果被跳过"直接生效），**没有新写一行免效果逻辑** |
| **`>N` 平减 N** | **`damageReduce` 旁边的平减** | `computeDamage` 的最终式多一项 `− flatReduce`，**最后才减**（`30 − 15 = 15` 是玩家会心算的式子；先减再乘比例会是 `(30−15)×0.45`，既不是需求写的规则也没人算得清） |

`BuffFlags.damageThreshold` 是新增的**一个数字**，多个来源取**最大值**
（与 `damageReduce` 同一条理由：相加会越过"完全免疫"，而且玩家无法预期）。

⚠️ **这个分工必须两边一致**：`flatBlocked` 返回 true 的那一击，
`resolveHit` **根本不调** `computeDamage`（改发 `avoided` 事件）。
这一点踩过一次：第一版让 `computeDamage` 自己把伤害减到 0，于是 `≤N`
那一半**永远不会走 `avoided`** —— 效果照样生效（"卸力了还是被晕"），
而且飘字显示 `-0`。`tests/unit/playerKits.test.ts` 现在把两半都钉住了。

### 3.4 新机制的"拒绝静默误用"

它是**引擎现在没有的概念**，所以按 `AGENTS.md` §2 的判据处理：

- `BuffFlags.damageThreshold` 的注释写明"两半各复用了哪条通路"
- 内容侧只有一个消费者（`kits/linwanfeng.ts` 的 `GUARD_THRESHOLD_BUFF`），
  值来自 `GUARD_THRESHOLD`（不是字面量）
- 有一条测试断言"**没有第二个技能带 `damageThreshold`**"——
  阈值是本作**唯一一处平减**，多出第二处必须是有意的

### 3.5 调参杠杆（两个数，**都是具名常量**）

用户给的杠杆，**当前都不改值** —— 他说的是"**如果**太强了"：

| 杠杆 | 常量（家） | 当前值 | 用户口径 |
|---|---|---|---|
| **阈值** `N` | `GUARD_THRESHOLD`（`data/balance.ts`） | **15** | 太强 → **10** |
| **按住消耗** | `GUARD_HOLD_DRAIN_PER_LOGIC_TICK`（`data/balance.ts`） | **3** | 太强 → **5** |

两条规矩：

1. **都住在 `data/balance.ts`，内容 import 它们** ——
   `kits/linwanfeng.ts` 里不许出现 `15` / `3` 这种字面量。改杠杆只能改一处。
2. **它们是"备用杠杆"，不是待办** ✓ —— 没有实测说"卸太强"之前不动。

⚠️ **按住消耗有一个已知的单位口径问题**（本次**没有**修）：引擎按
`holdDrain.perLogicTick` **每个逻辑步（0.1 秒）**扣 3 点，也就是实际
**30 炁/秒**；而设置页把同一个数当成 `/秒` 显示成 `3 炁/秒`
（`app/keyRows.ts` 的 `settings.detailCostPerSecond`）。
所以"太强 → 5"在引擎侧的含义是"每逻辑步 5 点"。这个偏差**单独重标定
一次**才该动（改它 = 改战斗数值），不要顺手修。

## 4. 「截」的派生去掉了（P3 计划）

用户原话：

> "当前的截本身就能派生击，这个我们放到 p3 或者初始化炁机的地方再实现，
> **把现在的截的派生去掉**。"

**做了什么**：

| 项 | 处理 |
|---|---|
| 「截」`onSuccess` 里的 `grantBuff: COMBO_WINDOW` | ❌ **删掉**（只剩"退还冷却"那一条） |
| `STRIKE`（「击」）本身 | ✅ **保留** |
| `COMBO_WINDOW`（派生窗口 buff） | ✅ **保留** |
| 文案（`skill.jie.desc`） | 删掉"并派生「击」"那半句 |

**为什么保留「击」与窗口**（`AGENTS.md` §2 的判据）：

| 性质 | 处理 |
|---|---|
| **未实现**：设计过、引擎还没有消费者 | **保留 + 标注**，并拒绝静默误用 |

所以 `kits/combo.ts` 的文件头**显式写着**"今天没有产出者，
P3 由炁机接回"，而后果被**变成机器可检查的**：

- `tests/unit/playerKits.test.ts` 断言"**全内容里没有任何东西会挂
  `combo-window`**" —— 谁在 P3 之前"顺手接上一个产出者"，这条先红
- 同一文件断言"「击」现在用不出来"（门禁以 `condition` 拒掉）——
  钉住现状，免得下一个人当 bug 修

⚠️ **今天「击」永远不可用**，这在界面上表现为"它根本不存在"
（`deriveSlots` 只在窗口开着时才插槽位）。这正是需要一条测试来记住
"它还在、而且是有意留着的"的原因。

**P3 要做什么**：炁机（`core/run/` 的候选池）在某个条件下授予
`COMBO_WINDOW`，那时「击」自动复活，**一键都不用改**。

## 5. 血量：W6 的状态（**做了**）

### 5.1 做了什么

| 项 | 之前 | 现在 |
|---|---|---|
| 上限来源 | `PLAYER_CAPS` = 全局常量 `HP_MAX = 100` | `playerCapsFor(id)`，血上限按角色（林晚风 **150** / 凯丽 **120**） |
| 谁读它 | `changeResource` 夹血读 `combatant.caps.hp` | **没变**（引擎侧的机制一个字没动） |
| `maxHp` 这个 stat | 算出来**没人读** | **仍然没人读**（见下） |

落地方式刻意选**最窄的那一种**：只把"上限值"参数化，
**不动资源结算的机制**。

### 5.2 为什么没走"把 `maxHp` stat 接线"

`docs/specs/2026-10-12-characters.md` §0.1 记的问题是双重的：

1. `HP_MAX` 是全局常量 ✗
2. `maxHp` 这个 `StatKey` **算出来没有任何人读**（`changeResource` 夹的是
   静态的 `combatant.caps`）✗

本次只解决了 (1)。**没有**把 `caps.hp` 改成"每 tick 从 `stats.maxHp` 同步"
—— 那会让**装备/增益动态改血上限**成为可能，但那需要的是一整套
"上限变化时当前血怎么处理"的规则（超出部分砍掉？保持比例？）。
那是**另一个功能**，不是"让两个角色血不一样"。

所以 `units.ts` 的注释里明确写着"`maxHp` 仍然算出来没人读，那是
'装备/炁机动态改血上限'才需要的机制"。

### 5.3 为什么不影响黄金基线（硬验收）

`tests/golden/replay.test.ts` **仍然全绿，且基线一分未动**
（`GOLDEN_OUTCOME` 与 `REPLAY_FORMAT_VERSION = 2` 都没改）。

原因很直接：黄金夹具**自己造单位**（`tests/golden/fixtures.ts` 的
`PLAYER_CAPS` / `makePlayer()`），**不读** `data/units.ts`。
所以"真实游戏的玩家血上限从 100 变 150"与黄金那一场无关。

⚠️ **这不等于"改血上限永远不动基线"**：等黄金夹具改用真实
`makePlayer` 时，它会立刻跟着动。那时要按用户的规矩办
（**停下来问**，不要自己重标定）。

⚠️ **2026-10-12 第二次重标定之后，上一段的历史结论就不再成立了**：
夹具已经改用**林晚风的 150 血**（`PLAYER_CAPS.hp = LIN_WANFENG_HP`），
所以"基线一分未动"只描述**第一次改动当时**的状态。现在的事实见 §6.4。

## 6. 「破」的现状：**待接线**（第二次重标定）

拆完之后有一类技能**掉在两套之外**：「破」（黛玄的，她还没做）
与「击」（派生技）。**「击」**按 §4 处理。**「破」**的处境不同。

### 6.1 第一版取舍（**错的判断，刻意留着**）

第一版的决定是：**「破」保留在 `PLAYER_SKILLS`（玩家技能全集）里**。
理由是它被**黄金重放**的参考策略当成打断技
（`interruptSkillId: 'break'`）。如果删掉：

- `roughlyUsable('break', ...)` 返回 false（技能查不到）
- 那段策略**再也不打断 Boss**
- 实测整场结果从 **"剩 20 血 / 5696 tick"** 变成 **"满血 / 5816 tick"**

而当时的硬验收是"`tests/golden/replay.test.ts` 必须仍然全绿"、
"**若动了黄金基线，停下来问我**" —— 于是选择"一分不动"。

**这个判断是错的**，而且错得比"重标定一次"更糟：

> 没有任何角色带「破」，所以黄金重放**测的是一个游戏里不可能发生的
> 场景**。绿色的测试因此给出**虚假的安全感** —— 它证明的是"这个不可能
> 的场景没有漂"，而不是"游戏没有坏"。

那一版的后果写在当时这里：

| 项 | 第一版 |
|---|---|
| 「破」的定义 | ✅ 保留在 `kits/reserved.ts` |
| 属于哪个角色 | ❌ 谁都不带 |
| 在 `PLAYER_SKILLS`（全集）里吗 | ✅ **在**（设置页能绑、黄金夹具能解析、基线不动） |

### 6.2 用户的选择 (B)：重标定一次

用户看过这个取舍后选了 **(B)**：

1. **黄金夹具改用林晚风建模**（她的 5 招，没有打断技）→
   `GOLDEN_OUTCOME` **重标定**（用户批准）
2. 「破」**不再进 `PLAYER_SKILLS`** —— 于是它
   **不属于任何角色、不可绑键、不出现在设置页**
3. 但**定义不删**：用户明确说过「破」将来归黛玄
   （`AGENTS.md` §2：这是"未实现 / 待接线"，不是"重复"）

⚠️ **`REPLAY_FORMAT_VERSION` 不 +1**（仍是 **2**）：这次重标定改的是
**期望值**，引擎的确定性语义一个字没动 —— 判据见
`docs/specs/2026-10-12-roguelike.md` §7.2「两个版本号，判据不同」。

### 6.3 现在的机制：第三个桶 `PENDING_SKILLS`

```text
PLAYER_SKILLS   两个角色的技能 + 派生技        → 注册 ✅  可绑 ✅
BOSS_SKILLS     两个 Boss 的招                 → 注册 ✅  可绑 ❌
PENDING_SKILLS  「破」（黛玄的，还没接线）      → 注册 ✅  可绑 ❌  属于任何角色 ❌
```

- 定义在 `src/data/kits/reserved.ts`，带 **`pendingFor: 'daixuan'`** 与
  **`blockedBy: 'owner-not-implemented'`** —— "它归谁、为什么今天接不上"
  是**字段**，不是注释（`blockedBy` 是英文短码：它是开发者元数据，
  而 `src/` 不许硬编码中文文案，i18n 规范 I1）
- 它仍在 `ALL_SKILLS` 里（**引擎按 id 解析得到**，黛玄接线时不用重建），
  但**不在 `PLAYER_SKILL_IDS`** —— 而"设置页列什么 / 什么可绑"的判据
  就是后者（`app/keyRows.ts` 的 `isBindablePlayerSkill`），所以它是
  **结构性**消失，不是特判
- `DEFAULT_BINDINGS` 里那条 `{ key: '', skillId: 'break' }` **删了** ——
  它是"没有角色的技能也能绑键"的来源

**可检查性**（`AGENTS.md` §2 要求"待接线"能被机器检查）：

| 断言 | 在哪 |
|---|---|
| 在 `PENDING_SKILLS` 里、`pendingFor` 是真实且 `DEVELOPING` 的角色 | `tests/unit/playerKits.test.ts` |
| 不属于任何角色（两套 kit 都没有它） | 同上 |
| 不在 `PLAYER_SKILLS` / `PLAYER_SKILL_IDS` 里 | 同上 |
| 定义仍在 `ALL_SKILLS`（注册表认得） | 同上 |
| **不在设置页的行里、不在 `DEFAULT_BINDINGS` 里、不可绑** | `tests/unit/keyRows.test.ts` |

### 6.4 黄金重放现在测什么

夹具是**真实的林晚风**（技能与血上限都来自她的 kit），参考策略是
**攒炁 + 闪避 + 用卸**，用上了她全部 5 招：

| | 旧夹具（不可能的场景） | 新夹具（林晚风） |
|---|---|---|
| 玩家 | 通用 100 血 + 「轰」+ **「破」** | 林晚风 **150 血** + 斩/劈/凝/卸/避 |
| 打断 | 有（用黛玄的技） | **没有**（她本来就没有） |
| `GOLDEN_OUTCOME` | 5696 tick / 剩 20 血 | **1436 tick / 剩 140 血** |

⚠️ 新基线**更短**（约 24 秒）的原因：劈（50 缠 / 45 伤）比轰（30 伤 + 易伤）
是更直接的缠出口；旧策略每次读条都朝「破」按一遍（10 炁，多数被霸体挡下）
白烧炁；而且旧优先级是 **凝 → 轰 → 斩**，而「凝」与「轰」都花 50 缠、
「凝」又没有冷却 —— 所以「凝」会**一直抢在「轰」前面**（本次顺手给参考
策略加了"增益还挂着就跳过"，两个技能才都真的用上）。
（详见 `tests/golden/fixtures.ts` 的 `GOLDEN_OUTCOME` 注释。）

⚠️ 这条基线**还剩多少价值**（诚实评估）：它仍然是"这一场战斗**逐位**
没变"的锚（种子、AI、门禁、数值、时长、终态血量），而且现在**测的是一个
真的能发生的场景**；但它的**防御侧信号变弱了** —— 全程只挨 10 点，
所以"承伤/闪避/卸力平衡变坏"未必能在这条上体现。那类性质由
`tests/unit/prideBoss.test.ts` 与 `tests/golden/encounter.test.ts` 守。

### 6.5 待接线的终态

等黛玄做完时：把 `BREAK` 移进 `kits/daixuan.ts`、把 `PENDING_SKILLS`
从 `ALL_SKILLS` 里拿掉即可 —— 那时它就有角色带了。
