## 2. A. 美术从哪来 —— 路线对比

### 2.1 四条候选路线

| | **A1 Retro Diffusion API** | **A2 本地 SDXL + pixl** | **A3 外部美术（人）** | **A4 A1/A2 + 人工精修** |
|---|---|---|---|---|
| **做法** | 调 `api.retrodiffusion.ai`，像素画原生模型 | 本机 M1 Pro 跑 SDXL + pixel-art LoRA，再用 pixl 吸附网格+限色 | 找人画 | AI 出草稿 → 人/Aseprite 清像素、修结构、统一色板 |
| **现金成本** | $0.03–0.18/张（实测价） | $0（电费 + 时间） | ¥200–800/张（市价量级，未询价） | 介于两者之间 |
| **时间成本** | 秒级/张 | **~7.5 s/张是 M4 Pro @512² 的数**；M1 Pro @1152×1536 估 10 倍以上 | 天/张 | 分钟–小时/张 |
| **风格可控性** | 中（`prompt_style` + 锁色板 + 参考图） | 中高（可本地训 LoRA） | **最高** | 高 |
| **可商用性** | ✅ 生成物自有（`rd_plus` 基座 Apache-2.0 系） | ✅ 同样自有 | ✅ 需签授权 | ✅ |
| **产能** | **高**（百张/天可期） | 低（M1 Pro 是瓶颈） | **极低**（人是瓶颈） | 中 |
| **上手难度** | **已跑通**（`artgen/generate.py` 可直接用） | 高（Rust 工具链未装、pixl crates.io 版本落后仓库 3 个月） | 低（外包） | 中 |
| **当前状态** | ✅ 已验证出图 | ❌ 未验证，Rust 未装 | ❌ 未接触 | ⚠️ 半跑通 |

### 2.2 推荐：**A4（Retro Diffusion 生成 + 本地像素化收尾 + 人工精修）**

**理由（按权重排序）：**

1. **它是唯一"已跑通"的路。** `artgen/generate.py` 能出图、能免费试算、能锁色板、能传参考图——这不是设想，是已经验证过的。A2 要现装 Rust 工具链并且 crates.io 版本滞后仓库 3 个月；A3 完全没启动。
2. **RD 是像素画原生，不是"像素风"。** 腾讯云 2026-01-13 的官方介绍原文：*"这些模型专门针对网格对齐、有限调色板的像素艺术进行训练"*。这一条直接消灭了"扩散模型出的是像素风、还得自己吸附网格"的整类问题。
3. **产能是碾压性的。** 7 个 Boss × 15 帧（架构 §8 的 idle4+attack4+hurt2+death5）在 A3 是几个月，在 A4 是**几天**。
4. **风格统一的抓手是现成的**：`input_palette`（锁色板）+ `reference_images`（锁角色，RD Pro 最多 9 张）+ 固定 `prompt_style`。这三样合起来正好回答"怎么保证 7 个 Boss 是同一个游戏里的"。

**但必须承认它的两个硬伤（都在 §7 开放问题里）：**

- **余额 $0.02**，不够出任何一张（最便宜的 `rd_fast` 也要 $0.03）。**必须先充值。**
- **人手精修这一步不能省。** 我们已经观测到**画风割裂**：RD 生成的玩家（平滑、细节多）和 FD2 的骑士（粗颗粒、强描边）放一起明显不是一套。AI 产出的一致性是"同源一致"，不是"同作画一致"——最终仍需要一个人做**统一的收尾**（对齐描边粗细、回收色板、修剪影）。

> **如果完全不愿投入人工**：那就接受"AI 原样产出"，但要接受「开放问题 #4」的观感风险。

### 2.3 关于 A2（本地 pixl）的定位

**不建议作为主产线**，但值得保留为**兜底**：
- 优点：无外部依赖、无外币、可离线复用无限次
- 缺点：M1 Pro 16 核 GPU 是硬瓶颈；且 pixl 的 `cargo install flow-pixl` 拿到的是 2026-06 的版本（仓库已推到 09 月），需 `--git` 安装
- **触发条件**：若 RD 充值/访问受阻，或产出量极大（>1000 张）时再启用

## 3. B. 7 宗罪 Boss 批量产出的风格统一方案

### 3.1 风格锚点：三件套同时在位

**缺任何一个都会漂。**

| 锚点 | 用什么 | 为什么不可省 |
|---|---|---|
| **① 风格** | **固定一个 `prompt_style`，全程不换** | 换 style 等于换画师。Boss 建议 `rd_plus__classic`（"强描边中分辨率像素画"——实测最贴 FD2 那种粗颗粒） |
| **② 色板** | `--palette <导出图>` → `input_palette` | **这是最有效的一致性杠杆**。它把 7 个 Boss 的颜色硬约束进同一套色，比任何提示词都管用 |
| **③ 角色** | `--reference <上一张>` → `reference_images`（**仅 `rd_pro__*` 支持，最多 9 张**） | 锁"同一个世界的人"。风格像了但配色/描边粗细不同，靠它收敛 |

### 3.2 色板从哪来（当前是缺口）

架构 §8 说 32 色从 `data/palette.ts` 导出，**该文件不存在**。所以坐标板这件事**必须先造锚**。两个选择：

- **(推荐) 造一张"美术基准色板"**：从既有 `theme.ts` 的 29 条语义色出发，扩到 32 色，存成一张 **PNG 色板条**（例如 32×1 或 8×4 的色块图），放在正式素材目录。它同时服务两件事：喂 `input_palette`，以及作为**代码侧唯一定义源**（替代 架构 §8 里那个不存在的 `data/palette.ts`）。
- **(不推荐) 拿某一张 Boss 的产出去提色**：会引入那一次生成的偏差，7 个 Boss 会围着它漂。

### 3.3 单个 Boss 的产出流程（可直接执行）

以「色欲」为例。**每步都先免费试算。**

```bash
# 0) 确认余额与风格目录（免费）
python3 artgen/generate.py balance
python3 artgen/generate.py styles rd_plus

# 1) 出站姿候选（先不要用参考图，找造型）
python3 artgen/generate.py estimate \
  --prompt "<只描述主体，例如：a slender demon of desire, horned, reclining, full body>" \
  --style rd_plus__classic --width 192 --height 256 --num 4
# 试算满意后再 gen

# 2) 定妆：从候选里选一张，存为 style anchor（这个 Boss 的"官方形象"）

# 3) 用参考图 + 色板出正式站姿（一致性在这里锁死）
python3 artgen/generate.py gen \
  --prompt "same character, standing idle, facing away from the viewer" \
  --style rd_pro__default --width 192 --height 256 --num 4 \
  --reference <上一步选中的.png> --palette <美术基准色板.png> --remove-bg

# 4) 用站姿当起始帧，派生动画（一次出整段，比逐帧便宜且更连贯）
python3 artgen/generate.py gen \
  --prompt "idle breathing" \
  --style rd_advanced_animation__idle --width 192 --height 256 --num 1 \
  --reference <定妆.png>
```

### 3.4 姿态预算（按 架构 §8 规范）

| 用途 | 架构 §8 规定帧数 | 建议产出方式 | 单价 |
|---|---|---|---|
| idle | 4 | `rd_advanced_animation__idle`（一次出整段） | $0.14/段 |
| attack | 4（前摇→挥击→命中→收招） | `rd_advanced_animation__attack` | $0.14/段 |
| hurt | 2 | `rd_pro__edit` 改站姿，或手改 | $0.18 |
| death | 5 | `rd_advanced_animation__destroy` | $0.14/段 |
| **地面预警标记** | — | 建议**程序化绘制**，不要生成（见下） | $0 |

> ⚠️ **UI 与几何元素不要交给 AI 生成。** 架构 §8 的"预警三通道"里的**地面标记**、血条框、字号、菱形台座，都是几何 UI——AI 出的是边缘毛糙、比例不稳的废品。项目本来就用 Pixi 程序化画这些（`BossSprite` 的 `armorLayers`、`parts/` 那一套），**继续程序化画**。这条能省掉大量返工。

### 3.5 保证"7 个是同一个游戏"的检查清单

每张定妆图过一遍，**任何一条不过就重出**：

1. **色板命中率**：把产出图降色到基准色板，看色差（若明显偏离，说明 `input_palette` 没生效或强度不够）
2. **描边**：外描边宽度一致（`classic` 风格是 1px 级）；不能有的粗有的没描边
3. **剪影测试**（架构 §8 强制）：**填纯黑仍能认出是哪个 Boss**
4. **明度区间**：7 个 Boss 的明度分布要重叠，不能一个惨白一个漆黑
5. **朝向与地平线**：脚底基线在同一 y，朝向符合"玩家在左、Boss 在右"
6. **⚠️ 无烘焙投影**（**H1**）：近黑占比 ≤ 2%（§5.6 的检查脚本），且**在提亮后的背景上看过**（H3）

## 4. C. 自有角色规模化（肉鸽前提）

### 4.1 核心原则：**美术与玩法解耦**

肉鸽的诉求是"不同角色 → 不同初始技能"。如果角色图与初始技能绑在一起，加角色就要动美术产线，加技能就要重出图。**必须拆开。**

**现状的有利条件**：`src/data/roster.ts` 的 `RosterEntry` **只有 `{ id, nameKey }`**，而且文件顶部明确写着"这里只放**元数据**，不放构造函数"，并强调依赖是单向的（`main` 读 roster，roster 不读任何人）。

**设计：在 roster 之外增加一层"美术键"，不要动 `RosterEntry`。**

```
roster.ts           { id: 'linWanfeng', nameKey: '...' }        ← 玩法身份（已有）
初始技能表（新）     { linWanfeng: ['slash','dodge',...] }        ← 玩法侧（新，纯数据）
美术表（新）         { linWanfeng: { dir: 'characters/linWanfeng', poses: {...} } }  ← 美术侧（新）
```

**为什么三者分开**：
- 加一个角色 → 只动 roster + 初始技能表 + 美术表，**互不阻塞**
- 改初始技能 → 不碰任何图
- 换某角色的形象 → 只改美术表，玩法零改动
- 美术表用**目录约定**而不是逐文件列举，这样加一个姿态不用改代码

⚠️ 不要把美术字段塞进 `RosterEntry`：那会破坏它"纯元数据、零依赖"的边界，也会让 `roster.ts` 反向依赖美术层。

### 4.2 骨架 / 比例 / 朝向规范（必须固定）

**新角色加入的成本，取决于这套规范有多硬。** 建议写死：

| 项 | 规范 | 依据 |
|---|---|---|
| 玩家背影画布 | **160×160** | 架构 §8 明文规定 |
| 锚点 | **底部中心**（`anchor.set(0.5, 1)`），脚底在 `PLAYER_BASE_Y = 456` | 现有实现 `playerActor.ts` 已如此 |
| 水平基准 | `PLAYER_CX = 300` | 同上 |
| 朝向 | **面朝右**（玩家在左、Boss 在右） | 现有实现把 FD2 帧镜像成朝右 |
| 绘制比例 | **必须 1.0**（禁止 `0.68` 这类分数缩放） | 见 §6.1 |
| 色板 | 同一张美术基准色板 | §3.2 |
| 剪影 | 填纯黑可辨认 | 架构 §8 |

**"面朝右"这条要用产线保证，不要用代码镜像。** 现在 `player-fd2-mirrored.png` 是镜像来的——镜像本身没问题，但如果每个角色都要在代码里判断"要不要翻"，就会积累特例。**规范写成"素材一律朝右"**，需要朝左的场合由渲染层统一处理。

### 4.3 每个角色至少需要几张图

| 姿态 | 现状 | 建议 |
|---|---|---|
| 站姿（idle） | ✅ 有（`player-fd2-mirrored.png`） | 必需 |
| 攻击帧 | ✅ 有（`player-fd2-slash.png`） | 必需 |
| 防御下沉 | ❌ 无 | 架构 §8 说要（玩家 3 帧：idle/闪避下沉/格挡抬盾） |
| 闪避 | ❌ 无 | 可用"下沉+横向位移"表达，**不必须单独出图** |
| 受击 | ❌ 无 | 可选（可用 tint 闪烁代替） |
| 技能特效 | ❌ 无 | 按技能数增长，**建议程序化绘制** |

**建议的最小美术契约：一个角色 = 2 张图**（站姿 + 攻击帧），其余用姿态变换/tint 表达。理由：现有实现已经这样跑通（`pose` 下沉 + `tint` 染色），扩大到 6 姿态会让"加一个角色的成本"涨 3 倍，而肉鸽需要的是**多加角色**，不是每个角色更精致。

**⚠️ 契约里必须含的两条硬约束**（否则加角色越多，坑越大）：

- **不带烘焙投影**（**H1**，见 §5.5）——角色要能放到任意背景上。这一点对肉鸽尤其致命：每换一次背景就要重擦一遍所有角色的投影
- **干净 alpha**（**H2**，见 §5.6）——近黑占比 ≤ 2%，边缘无半透明彩边

> ⚠️ 这与 架构 §8 的"玩家背影只 3 帧"不冲突——3 帧是上限，2 帧是当前落地的子集。**若接受本文的"最小契约"，需要同步把 架构 §8 那一行改掉**，否则规范与实现长期不一致。

### 4.4 加一个新角色的 checklist

1. `roster.ts` 加一条 `{ id, nameKey }`
2. `zh-CN.ts` 加名字文案
3. 初始技能表加一条
4. 美术表加一条（指向素材目录）
5. 出 2 张图（站姿 + 攻击帧），过 §3.5 检查清单
6. **不动任何渲染代码**

**验收标准：如果第 6 步需要动代码，说明解耦没做到。**

## 5. D. 背景图方案

### 5.1 目标分辨率

**必须满足：能被 960×540 整除出整数倍。**

| 候选 | 放大到 960×540 的倍数 | 评价 |
|---|---|---|
| **320×180** | **×3** | **推荐**。颗粒最粗，与 FD2 时代（320×200）同量级 |
| 480×270 | ×2 | 备选。细节多一些，颗粒感弱 |
| 960×540 | ×1 | ❌ 不是"像素画背景"，是高清插画 |

**推荐 320×180（×3）**，理由：
- FD2 的战斗背景是 **320×100**（背景层）+ 320×200 全屏。320×180 是与它同代同量级的比例，移植观感最接近
- ×3 意味着**每个美术像素在 canvas 上占 3×3**，画面上像素块清晰可数——这正是"像素画"的观感来源
- 角色（架构 §8 的 144×192 / 160×160）画在 960×540 上，与 ×3 背景的颗粒度**差 3 倍**。⚠️ **这是个真实冲突，见 §5.4**

### 5.2 与角色风格统一的手段

1. **同一张美术基准色板**（§3.2）—— 背景与角色的颜色来自同一套 32 色
2. **同一个 `prompt_style` 家族**，背景建议 `rd_plus__environment`（实测目录：**64–512px，one-point perspective scenes with outlines**）——"with outlines"与角色的强描边一致
3. **描边策略一致**：角色有外描边 → 背景里的前景物体（柱子、平台）也要有；远景可以没有（这是"选择性描边"，见像素画规范里的 outline 一致性）

### 5.3 亮度提升的具体手段

**要求是"稍微明亮一点"，不是"变亮"。** 现状 `bgTop=0x0a0c16` / `bgBottom=0x1e141c` 亮度约 **4% / 10%**，几乎是纯黑。

**手段（按推荐顺序）：**

| 手段 | 做法 | 注意 |
|---|---|---|
| **① 抬暗部，不抬亮部** | 把最暗值从 ~4% 提到 **18–22%**，最亮保持 | 避免"整体变灰"。像素画的明度层次靠暗部展开 |
| **② 加"高度渐变"** | 顶部偏冷亮（天空/顶光）、底部偏暖暗（地面反光） | 与现有 `bgTop/bgBottom` 的结构一致，只是数值上调 |
| **③ 结构剪影保留但提亮** | 现有那几根暗柱 → 改成 **明度 25–35% 的中景剪影** | 让背景有层次而不空 |
| **④ 加一层远景光晕** | 一个低饱和的径向渐变（不是纯色块） | 打破"纯色平面"的廉价感 |

**关键约束：别把前景角色淹掉。** 用**明度 + 饱和度双重分离**：

| 层 | 明度上限 | 饱和度 | 理由 |
|---|---|---|---|
| 背景（远景） | **≤ 45%** | **低**（降到 30–50%） | 低饱和 = 视觉后退 |
| 背景（中景剪影） | ≤ 35% | 最低 | 剪影本就该是"退"的 |
| **角色 / Boss** | **55–90%** | **高（保持）** | 高饱和 + 高明度 = 视觉前进 |
| 预警元素 | 高 + 独立高饱和色 | 最高 | 架构 §8："预警色独立且高饱和" |

**验收**：把成品转灰度，**角色仍应比背景亮**。若灰度下角色融进背景，说明明度分离不够。

### 5.4 ⚠️ 颗粒度冲突（必须拍板）

| 元素 | 每美术像素占 canvas |
|---|---|
| 背景 320×180 ×3 | **3×3** |
| 角色 160×160 ×1（架构 §8 规定尺寸） | **1×1** |

**两者差 3 倍**：背景是大色块、角色是细像素，放一起会像"低分辨率背景图贴了张高分辨率角色"。

**三个解法（择一，需拍板）：**

- **解法 1（推荐）：角色也走 ×3。** 角色按 **320×180 世界里的尺寸**出图，即架构 §8 的 160×160 改为约 **53×53**，绘制时 ×3。**代价**：架构 §8 的尺寸要改；角色细节大幅减少。**收益**：全画面颗粒统一，最像真像素游戏。
- **解法 2：背景走 ×1，即 960×540 高清。** 放弃"背景是像素画"，改成"像素角色 + 高清环境"。**代价**：与 架构 §8 的像素美术定位冲突。
- **解法 3：背景 ×2、角色 ×1。** 折中（差距 2 倍）。颗粒不统一但比 3 倍好。

> 本文**推荐解法 1**（全画面 ×3），因为它是唯一让"像素画"这个定位自洽的选项。但它**会改变 架构 §8 的角色尺寸**，所以列为开放问题。

### 5.5 ⚠️ 投影归属：**精灵一律不带烘焙投影，由引擎画**（硬性）

**这一条必须在美术规范里定死**，否则会在"背景提亮"的那一刻集中爆掉。

#### 实测证据（可复核）

对当前占位素材逐个统计「不透明纯黑 `(0,0,0)` 像素」：

| 素材 | 不透明像素 | 纯黑 | 占比 |
|---|---|---|---|
| `player-fd2-mirrored.png` | 22196 | **4824** | **21.7%** |
| `player-fd2-slash.png` | 32168 | 6180 | 19.2% |
| `boss-fd2-knight.png` | 22196 | 4824 | 21.7% |
| `boss-fd2-follow.png` | 26640 | 6068 | 22.8% |
| **`player-back-rd.png`（RD 生成）** | **917** | **0** | **0.0%** |

> **最后一行是关键对照**：RD 生成的素材纯黑占比 **0%**。所以那些黑块**不是像素画的必然，是 FD2 原素材把"脚下抖动(dither)地面阴影"烘焙进精灵**的产物。

**对比实证**（把同一张精灵放到三种明度背景上）：

| 背景 | 结果 |
|---|---|
| 当前 `bgTop/bgBottom`（亮度 ~4%/10%） | 投影**几乎看不见**（黑压黑） |
| 提亮到 ~20%/28% | 脚下立刻出现**黑色抖动条** |
| 再亮到 ~38%/45% | 变成**一坨明显的黑色污渍**，像渲染 bug |

#### 为什么**不能**靠后处理清掉它

用 8 邻域连通分量分析 `player-fd2-mirrored.png`：

```
连通分量数：4      面积降序：[22104, 80, 8, 4]
4824 个纯黑像素全部落在【分量 #1 —— 主分量（身体）】里
```

**投影与角色身体是焊死的**（只差那 20 个黑像素落在小分量里）。所以"删除独立小连通块"这类清洗手段**无效**。

#### 决策

| 方案 | 内容 | 代价 |
|---|---|---|
| A. 精灵自带投影 | 投影必须**半透明**（alpha 30–50%）或**染成环境色**；**绝对禁止不透明纯黑** | 每张图都要单独控制；换背景时投影颜色可能不搭 |
| **B. 精灵不带投影，引擎画**（**推荐**） | 精灵必须**完全没有地面接触阴影**；引擎用椭圆/渐变画通用投影 | 需在 `src/render/` 加一处投影绘制（渲染层改动） |

**推荐 B**，理由：

1. **背景要换**（本次需求就是提亮背景）——引擎画的投影能自动适配任意背景明度
2. **角色会变多**（肉鸽前提，§4）——引擎投影保证所有角色在任意背景上一致，不必逐张重出
3. **素材侧更简单**：AI 生成要"半透明 alpha 30–50% 的投影"是很难稳定达成的（扩散模型不擅长精确 alpha），而"**不要有投影**"是一句就能写进 prompt 且容易校验的约束
4. 与 §6.1 的"禁止非整数缩放"同源：**把易变的、与背景耦合的东西从素材里拿出来，交给代码**

**⚠️ 已知的现实代价**：现有 FD2 占位素材的投影**已焊死、无法自动清除**。所以：
- 在**正式素材就位前**，要么**先不提亮背景**，要么接受那坨抖动
- 若必须提前提亮：只能在 Aseprite 里**手工擦除**（对 202×232 的图约几分钟），或换用纯黑占比 0% 的 RD 素材
- 这条是**优先做正式素材的又一个理由**

### 5.6 精灵交付校验（**两条强制关卡**）

**关卡 1：alpha 洁净度检查**（交付前必跑）

判据：**不透明区域里的纯黑/近黑大面积块**。参考实现（可直接用）：

```python
from PIL import Image
import numpy as np

def shadow_report(path, dark_threshold=45, warn_ratio=0.02):
    """返回 (不透明数, 近黑数, 占比)。占比 > warn_ratio 即判定携带烘焙投影。"""
    a = np.asarray(Image.open(path).convert("RGBA")).astype(int)
    opaque = a[:, :, 3] > 0
    n = int(opaque.sum())
    dark = int(((a[:, :, :3].sum(axis=2) < dark_threshold) & opaque).sum())
    return n, dark, (dark / n if n else 0.0)

# 逐个素材跑：占比超过 2% 就拦下
```

**判据阈值**：**近黑占比 > 2% 即拒绝入库**。依据：RD 生成的干净素材是 **0%**，而携带烘焙投影的素材是 **19–23%**——两者之间有巨大空档，2% 是个安全的分界。

**关卡 2：在提亮后的背景上验收**

**不要在当前近黑背景上看图验收。** 必须先把目标背景的明度调到位，再把角色放上去看。理由：这个坑在当前背景下**完全不可见**，会一直潜伏到最后换背景时才爆。

验收方法（任选）：
- 用 `artgen/` 的合成脚本把素材贴到提亮后的背景色上，`read_image` 目视检查
- 或不依赖工具：把素材放在**明度 ~40% 的中灰**上看——HDRI 式的"中性背景"能同时暴露亮部和暗部问题

**附加检查**（与 §3.5 的检查清单并列）：
- **半透明像素**：像素画若为硬边，边缘不应有 alpha 在 1–254 之间的"半透明彩边"（会在换背景时产生光晕）
- **色板命中**：降色到美术基准色板后的色差

## 6. E. 落地与工程约束

### 6.1 ⚠️ 分数倍缩放：分两层处理（**这是本文最关键的技术结论**）

**必须区分两个不同的缩放环节**，它们的成因和解法完全不同：

```
美术原生分辨率 ──[环节①]──> canvas 960×540 ──[环节②]──> 屏幕 CSS 像素
                    素材/代码可控              架构问题
```

#### 环节①：美术 → canvas（**可立即修，且必须修**）

**问题**：`playerActor.ts` 的 `SPRITE_SCALE = 0.68`。

原图 202×232 × 0.68 = **137×158 渲染**。`nearest` 过滤下做 **0.68 倍的缩小**，意味着**每 100 个源像素里有 32 个被直接丢弃**——素材自己的像素网格在进入 canvas 之前就被打乱了。代码注释里其实已经承认了这件事（"旧值 0.42 丢了 58% 的像素"），但 0.68 仍在丢。

**解法（不需要改架构，只需要改素材和常量）**：

1. **素材按 架构 §8 的目标尺寸出图**（Boss 144×192、玩家 160×160），绘制时 `SPRITE_SCALE = 1.0`
2. **禁止任何非整数缩放**：允许 `1`、`2`、`3`；不允许 `0.68`、`1.5`
3. 若素材比目标大，**先在 Aseprite 里用最近邻整数倍缩到目标尺寸再入库**，而不是在运行期缩

> 这条是**投入最小、收益最大**的一条：改一个常量 + 重出素材，立刻消除当前最明显的糊。

#### 环节②：canvas → 屏幕（**架构问题，需拍板**）

**问题**：`src/render/scaling.ts:35-38`

```ts
const fit = Math.min(viewportW / LOGICAL_W, viewportH / LOGICAL_H);
return mode === 'integer' ? Math.max(1, Math.floor(fit)) : fit;
```

`src/main.ts:65` 硬编码 `SCALING_MODE = 'fit'` → **分数倍**。在 1440×900 的窗口里 `fit = 1.5`，于是 canvas 里 1 个像素在屏幕上占 **1.5 个设备像素**——有的像素占 1 个、有的占 2 个，**像素宽度不均匀**。

**已被缓解的部分**：`styles.css:33` 的 `image-rendering: pixelated` 保证了**不糊**（没有线性插值）。所以现状是"**锐利但不均匀**"，不是"糊"。

**三个选项**：

| 选项 | 做法 | 代价 |
|---|---|---|
| **① 保持 `fit`**（现状） | 不变 | 非整数倍视口下像素宽度不均（1 px vs 2 px 交替） |
| **② 改默认 `integer`** | `main.ts:65` 改成 `'integer'` | 四周出现黑边（1440×900 下只有 960×540 ×1，浪费 44% 屏幕） |
| **③ 把空壳设置接上**（推荐） | 让玩家自己选；默认仍 `fit` | 需要实现 UI（i18n 文案已存在，见 D3） |

**推荐 ③**，理由：
- `architecture.md 架构 §10.2` **已经论证过默认 `fit` 的理由**（"始终填满屏幕"，且 1920×1080 → 2.0、3840×2160 → 4 这些常见分辨率下恰好是整数）
- i18n 文案 `scaleFit` / `scaleInteger` **已经写好了**，UI 未接——这是**半成品**，补齐成本低
- 在意绝对锐利的玩家可以切 `integer`，两者都保留

> ⚠️ 注意 架构 §10.2 原文写"`fitScale` 恰好是整数（2/2.667/4）"——**2.667 不是整数**，这句是自相矛盾的。2560×1440 下 `fit = 2.667`，像素宽度会不均匀。这条建议一并订正。

### 6.2 素材放哪

## 8. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **AI 产出风格漂移** | 7 个 Boss 不像一套 | 三件套锚点（§3.1）+ 每张过 §3.5 检查清单 |
| **分数倍缩放未修** | 真像素画被毁（**当前最实际的糊**） | §6.1 环节①：改素材尺寸 + `SPRITE_SCALE=1.0`，成本极低 |
| **`BattleScene.ts` 只剩 25 行** | 加功能必触 700 行上限 | 新代码一律进新文件；触线时按 AGENTS.md §3 **拆 util，不许删注释** |
| **`prompt_style` 换来换去** | 风格失控 | 把 style 写成产线常量，不许临时改 |
| **背景提亮过头** | 前景角色被淹 | §5.3 的明度/饱和度双重分离 + 灰度验收 |
| **版权素材误入库** | 法律风险 | §6.6 三条铁律 + 上线前搜检 |
| **⚠️ 烘焙投影在提亮背景时集中爆掉** | 素材看似正常、换背景后满屏黑色抖动；且**无法自动清除**（与身体焊死） | **H1 硬性禁烘焙投影** + **H3 在提亮后的背景上验收**（§5.5 / §5.6） |
| **H2 校验缺失导致脏 alpha 累积** | 角色越多越难回头清；换背景时逐张返工 | 交付前跑 §5.6 的检查脚本，**>2% 直接拒收** |
| **渲染层投影改动落在 `BattleScene.ts`** | 该文件只剩 25 行余量，会立刻触 700 行上限 | 投影绘制进新文件（如 `src/render/groundShadow.ts`），由 actor 内部挂载，不动 `BattleScene.ts` |
| **RD 服务不可用/涨价** | 产线中断 | 保留 A2（本地 pixl）作兜底；素材与 prompt 记录在 `public/art/README.md` 以便换工具重出 |

## 9. 建议的推进顺序

1. **先修环节①缩放**（改素材尺寸 + `SPRITE_SCALE=1.0`）——**投入最小、收益最大**，且不依赖充值
2. **造美术基准色板**（§3.2）——它是后续所有一致性动作的锚
3. **充值 RD，出 1 个 Boss 走通全流程**（定妆 → 参考图站姿 → 动画）——**验证产线，而不是先铺 7 个**
4. **把 架构 §8 的 4 处脱节（D1–D4）订正**——否则规范会持续误导后来者
5. 产线跑通后再批量铺 7 宗罪 + 背景

**⚠️ 一条顺序铁律**：**「提亮背景」必须排在「换掉 FD2 占位素材」之后。**
现有占位素材的投影已焊死（§5.5），提前提亮背景 = 先给自己看一坨黑色抖动。
若必须提前看提亮效果，请先用纯黑占比 0% 的 RD 素材替换玩家（`player-back-rd.png` 就是现成的）。
